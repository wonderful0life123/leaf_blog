# 日常发布免编译验证

> 历史实验记录。已由正式实现替代，原临时脚本已移除。当前入口为 `pnpm runtime:build` 与 `pnpm runtime:test`；部署及兼容边界见 [RUNTIME_PUBLISHING.md](../../deploy/studio/RUNTIME_PUBLISHING.md)。以下耗时与说明对应实验当时的版本。

2026-10-14。本目录是隔离实验，尚未接入 Studio 正式发布。没有推送 GitHub、修改生产配置或访问生产草稿库。

## 结论

**当前博客可以用 Astro 官方运行时渲染和 live content collections，在不重新编译、不重启进程的情况下更新文章。** 已保留现有 Firefly 文章模板、导航、分类、代码高亮和数学公式。无需为了发布速度更换博客主题。

这证明可以避开当前发布中约 2 分 40 秒的全站编译步骤，尚不能将下面的本地耗时视为服务器完整发布耗时。

后续完整发布流程的隔离集成结果见 [PIPELINE.md](./PIPELINE.md)：已复用 Studio 发布接口及真实本地 Git，补上 RSS、站点地图、搜索更新和失败恢复验证。下面保留第一轮单纯渲染实验的结果与当时边界。

## 方法与实测

- 使用实际项目 Astro 6.1.9，临时安装兼容的官方 `@astrojs/node@10.0.6`。未改项目依赖或锁文件。
- 将当前 Git 可见工作文件复制到临时目录，在副本中接入 Node adapter、`defineLiveCollection`、`getLiveCollection` 和 `render`。
- 执行一次真实生产构建，再启动构建后的 Node 服务；没有使用开发服务器热更新。
- 编译后才新增文章和 PNG，再修改正文、标题、摘要、分类，最后删除并恢复文章。
- 同一路径读取更新，不使用随机查询参数；所有请求均在同一服务进程完成，编译产物 SHA-256 始终不变。
- Markdown 渲染结果按内容及元数据哈希复用，返回值复制后交给主题，避免主题的上一篇/下一篇计算修改缓存。

本机单轮结果；不是统计分位值：

| 场景 | 文章响应 | 首页响应 | 元数据接口 | 写入并完成整组验证 |
| --- | ---: | ---: | ---: | ---: |
| 新增文章 | 33 ms | 19 ms | 5 ms | 111 ms |
| 修改正文 | 26 ms | 20 ms | 4 ms | 93 ms |
| 修改标题、摘要、分类 | 22 ms | 18 ms | 3 ms | 86 ms |

首次代码构建 10.535 秒；服务启动后的首次首页请求 632 ms。各轮内容更新没有执行构建。整组验证包含写入、HTTP 请求及断言、图片请求和产物哈希检查，不包含 GitHub 推送。

原始数据见 [results.json](./results.json)。浏览器另行确认了更新后的真实文章模板、分类、代码高亮、公式排版；测试图片为 1×1 PNG，用于验证构建后新增媒体可访问，不代表完成了图片显示与优化验收。

## 可重复执行

在项目根目录执行：

```sh
node experiments/live-publishing/run.mjs
```

首次需要访问 npm 官方仓库；需允许监听本地回环地址。结果和构建日志写入输出中标明的临时目录。正常完成后服务自动退出，诊断目录保留。

如需浏览器检查，使用 `node experiments/live-publishing/run.mjs --serve`。输出包含实际地址；向运行脚本发送 SIGTERM 后会关闭实验服务。实验使用独立端口，不影响现有 4321 Studio 开发服务。

## 正式接入仍需完成

1. **发布事务。** Studio 预览确认、GitHub 提交、发布快照及图片切换必须有明确的成功状态、冲突处理和失败恢复。草稿不进入公开快照。实验只验证了文件快照的原子替换及草稿过滤。
2. **所有内容入口。** 首页、文章和元数据接口已验证；RSS、站点地图、Pagefind 搜索索引仍是构建时产物，尚未更新。归档路由已改为运行时，但完整交互未单独验收。不能直接用本实验替代生产发布。
3. **运行方式与缓存。** 公开动态页面需要常驻 Node 服务，并由 Nginx 转发。实验明确使用 `no-store`，没有验证 CDN 失效。正式方案需处理公开页面缓存和更新，避免每位访客重复承担渲染开销；私密 Studio 与预览保持独立鉴权和缓存隔离。
4. **兼容与性能边界。** 尚未覆盖 MDX、旧文章相对图片路径、Astro 图片优化、并发发布、大规模文章、生产 CPU 竞争以及完整主题功能。当前 loader 每次读取整个快照，适合可行性验证，不能据此推断大规模吞吐量。

建议下一轮先把这条路径接入隔离的 Studio 发布流程，测量从确认发布到 GitHub 提交及公开页面更新的完整耗时，再决定生产切换。代码部署与内容发布分开：主题或功能代码变化仍需要构建，日常内容变化通过发布快照更新。
